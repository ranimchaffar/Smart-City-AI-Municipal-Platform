The scenario

A citizen sends a photo of an urban problem (pothole, leak, broken streetlight...) along with a voice or text message via Telegram. In under a minute they receive an acknowledgment with a tracking number. On the municipality's side, a structured ticket — already classified, prioritized and routed to the right department — appears in a shared tracker.

Why Telegram rather than WhatsApp

The WhatsApp Business API requires a Meta business verification that is impossible to obtain in 5 weeks. The Telegram Bot API is free, instant, and n8n's Telegram Trigger node natively handles photo + audio + text — which makes a real live demo actually feasible on defense day.

Why this output "matters" to the jury

Not just a chatbot

The output is a concrete artifact independent of the chat: a headered PDF ticket, a row in a Google Sheet/Trello visible to the whole team, an acknowledgment with a case number.

Traceable end to end

Every step (transcription, vision, classification, retrieval, formatting) is a visible, replayable n8n node — useful for the 10-minute Q&A where every member must be able to answer on any part.

Categories covered

Potholes / damaged roads · damaged sidewalks · broken signs · defective street lighting · illegal waste · damaged urban furniture · visible water leaks

Justification (for the report)

A single orchestrator would need to handle transcription, vision, classification, retrieval and formatting in one giant prompt — undebuggable and impossible to document prompt by prompt (20% of the grade). The sequential split with a router isolates each failure and allows independent iteration per prompt, exactly what the brief asks for ("show a before/after per key prompt").

Anticipate in Q&AWhy not a hierarchical orchestrator? Because the flow is inherently linear (an image cannot be routed before it is classified) — a master-worker setup would add complexity with no benefit for this use case.
Extension — 6th agentA Follow-up Agent can be added after the Report Agent to monitor the ticket's lifecycle (see the Differentiators tab). Easily justified as a natural evolution of the sequential chain.

n8n workflow structure

Node by node, ready to implement

1 Telegram Trigger

Listens for new messages (photo, voice, text) sent to the project's bot.

2 Switch — message type

Routes based on photo / audio / text to prepare the right downstream processing.

3 HTTP Request → Whisper

Transcribes the audio into text if the message is a voice note.

4 HTTP Request → VLM (Vision Agent)

Sends the image + structured prompt, receives a JSON {category, severity, description}.

5 Function node — Router Agent

Maps the detected category to the concerned municipal department via a rules table.

6 HTTP Request → Vector Store

Queries the RAG (top-k) with category + description as the query.

7 HTTP Request → LLM — Report Agent

Composes the final structured ticket from all accumulated context.

8 HTML → PDF

Generates the final ticket PDF with a municipal letterhead, ready to archive.

9 Google Sheets / Trello

Adds a row or card to the shared tracker, visible to the whole team.

10 Telegram — reply

Sends the citizen the acknowledgment with their case number.

Node 11 — global Error TriggerCatches failures from any node in the pipeline and notifies the team on a dedicated Telegram/Slack channel. Showing it visibly in the exported JSON proves error handling was designed, not improvised — a good point for Q&A.

Differentiators

What takes the project beyond a plain "report → ticket" pipeline

1 · Automatic duplicate merging

If several citizens report the same issue within a close radius within 48h, the system merges them into a single ticket with a report counter, instead of creating several.

Implementation: before the Report Agent, a node compares the embedding of the new description + GPS distance against recently opened tickets in the vector store; above a similarity threshold, it increments the existing ticket rather than creating a new one.

2 · Follow-up Agent — the ticket has a lifecycle

A 6th agent that automatically escalates if the announced deadline is missed, turning the system from "generates a document" into "manages a process".

Implementation: daily Schedule Trigger node + Wait, checking the tracker's status; on overdue, it re-pings the assigned department and notifies the citizen via Telegram.

3 · Reply in the detected language/dialect

The system detects whether the message is in Modern Standard Arabic, Tunisian derja, or French, and replies in the same language — real citizen accessibility.

Implementation: a language-detection prompt upstream of the Report Agent, whose output selects the Telegram reply template.

4 · Context-aware prioritization via OSM

The Router Agent adjusts priority based on proximity to a school, hospital, or busy road, rather than a fixed category→priority mapping.

Implementation: HTTP Request node to the Overpass API (OSM) with the report's GPS coordinates, result injected into the Router Agent's prompt.

5 · Public transparency map

A simple view of open reports by neighborhood — a civic-tech gesture beyond an internal municipal tool.

Implementation: a read-only published Google Sheet, or a small web page fed by the same tracker used by the Report Agent.

For the defenseIdeas 1 and 2 are the ones to lead with: they add the most technical depth (new reasoning, a justifiable new agent) for the implementation effort involved.

Chunking strategy (compare, valued by the brief)

StrategyDetailAdvantage / limit
Structural (chosen)Split by article/section, ~400-500 tokens, ~50 overlapPreserves legal meaning; harder to automate on poorly structured text
Fixed size (comparison)512 tokens, 50 overlap, no structural awarenessSimple to implement; can split an article in half and lose meaning

Embedding & vector store

  • Embedding: multilingual model (multilingual-e5-large or text-embedding-3-small) — corpus in French, citizen messages potentially in Arabic/Tounsi
  • Vector store: Chroma or Qdrant, called from n8n via an HTTP Request node
  • Retrieval: top-k=3, no reranking in v1 (justified as a deliberate simplicity trade-off)

Retrieval evaluation (mandatory deliverable)

10 to 15 test queries such as "water leak on street X", "dangerous electrical pole", "broken sidewalk near school" — manual relevance scoring of the top-3 results, logged in a table with comments.
